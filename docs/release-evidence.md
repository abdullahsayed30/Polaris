## Evidence record format

For each result retain:

- Full source commit and PR/run URL. For an unmerged branch, name that branch and do not imply the result came from `main`.
- Capture timestamp with timezone; OS/architecture; Java, Maven Wrapper, Docker/Compose and relevant tool versions; configuration/overrides and image IDs or digests, excluding secrets.
- Working-directory/clean-clone provenance, exact command, exit status, test counts/failures/skips and a durable output/artifact link.
- Scenario identifiers: order/reservation ID, event ID, request ID and trace ID. Include dashboard time range and query, trace JSON/spans and persisted before/after assertions as appropriate.
- Observed result, cleanup performed and limitations. State whether evidence was inspected directly or supplied by the validating owner.

Keep artifacts at a stable repository path or release attachment and link them here. GitHub Actions artifacts expire (see [CI/CD retention](ci-cd.md)); preserve the selected reports and SBOMs before relying on them for a lasting portfolio claim. Local temporary logs are useful for diagnosis but are not durable release evidence. Re-run affected scenarios on the final combined candidate; unrelated branch results cannot establish that candidate's runtime behavior.

## Reproduction and release gate

Select the exact approved candidate commit, rather than a moving branch:

```bash
git clone https://github.com/abdullahsayed30/Polaris.git polaris-evidence
cd polaris-evidence
# Replace REVIEWED_COMMIT with the full approved commit SHA.
git checkout --detach REVIEWED_COMMIT
git rev-parse HEAD
java -version
./mvnw --version
docker version
docker compose version
./mvnw -B -ntp spotless:check checkstyle:check test
./mvnw -B -ntp verify
git diff --check
```

These are required reproduction commands, not recorded passes. Use the [Quick Start](../README.md#quick-start) and [authenticated demo](../demo/README.md) for runtime commands in a dedicated fixture. Schedule one Maven reactor per checkout and one owner per Compose environment. Full verification needs Docker; confirm integration suites executed instead of relying on `BUILD SUCCESS` with skipped tests.

Before declaring the candidate ready, all required checks must pass on its exact head, the user must approve review, and the runtime rows above must identify retained evidence or an explicitly accepted release limitation. Apply Compose/Helm validation to relevant deployment changes; rendered manifests are not a live cluster check. Choose the version/tag only after the combined scope is reviewed. Tag creation, GitHub release publication and repository settings require their own approval of the concrete proposal in the release draft.
