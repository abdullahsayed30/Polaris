## Recovery evidence required for the story

Use the validated local recovery procedure supplied with the observability evidence. Retain a timeline of the failed request, committed `PENDING` order, dependency/process restoration and worker resolution **without another client create request**. Verify the same order and reservation identity, stock quantity, single finalization/outbox insertion and terminal inbox result. Inspect each database independently; application services must never gain cross-service database access.

A temporary inventory outage can exercise pending recovery, but does not by itself demonstrate an inventory commit followed by a lost response. The retained live case exposed a static gRPC resolver failure after a single Order restart while Inventory was absent: automatic discovery did not recover after Inventory returned. An extra Order restart recovered the original identity/carrier. Keep this historical failure and manual step visible; the separate DNS regression below does not turn these old captures into automatic live recovery proof. For the lost-response/finalization failure windows, also reference the Docker-backed order integration tests. Mocks or a dashboard screenshot alone do not prove committed transaction behavior.

## Capture checklist

- Keep a recording or artifact link, capture timestamp/timezone, exact commit, environment and commands in the evidence index.
- Preserve numeric metric values, dashboard time range and raw trace JSON alongside screenshots when available; an empty dashboard or healthy Tempo endpoint is not trace evidence.
- Keep command exit statuses and integration-test counts including skips. A skipped Docker suite is not a pass.
- Refresh tokens privately and exclude tokens, private credentials and personal customer data from retained output.
- Do not reset shared volumes, purge topics or alter business rows to make the demonstration appear successful. Record failure and cleanup actions truthfully.
