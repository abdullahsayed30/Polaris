## Proposed release narrative

Polaris is a production-oriented microservices reference template for a demo order journey. Java 25 / Spring services demonstrate explicit service/database ownership, authenticated REST at the gateway, generated internal gRPC and durable Kafka events. The portfolio presentation connects architecture choices to reproducible evidence rather than claiming production operation.

Available on the inspected baseline:

- BuckPal-style hexagonal internals for order, inventory and notification: explicit ports, plain models, separate JPA entities/mappers and root Spring wiring. Gateway, shared and generated protobuf remain outside the restructuring; no Spring Modulith was adopted ([ADR 0021](../adr/0021-adopt-hombergs-hexagonal-service-structure.md)).
- Customer-scoped HTTP idempotency, atomic order-keyed stock reservations and durable pending-order recovery using the original identity ([ADR 0020](../adr/0020-recover-pending-orders-durably.md)).
- Transactional outbox/inbox delivery, at-least-once Kafka semantics, stable event identity and acknowledged DLQ publication ([ADR 0019](../adr/0019-use-transactional-outbox-and-consumer-inbox.md)). Notifications remain simulated.
- Reviewable HTTP/event/protobuf contracts, legacy-event compatibility and exact-decimal regressions; service-owned Liquibase migrations remain immutable.
- Production runtime and Jackson security-gate fixes in [PR #6](https://github.com/abdullahsayed30/Polaris/pull/6), with quality/security gates retained. Scan results describe a specific dependency/image snapshot, not permanent security assurance.

## Known limits

- Local Keycloak users/password grant, HTTP and plaintext infrastructure are development fixtures. Notification handlers simulate delivery; real providers need provider-side idempotency.
- Operational SLOs and resource settings are proposed objectives/starting points. No measured production availability, latency, capacity or benchmark is claimed.
- Spring CVE-2026-47884/47890/47892 remain in the installed versions and raw reports under the explicit temporary ADR 0017 gate-only accepted risk. Enforce the exact scope/expiry; reassess or patch before the cutoff. Historical green runs remain valid only for their recorded source and scan snapshot.
- Order resolution holds a local row lock across a bounded RPC; this is a documented low-throughput tradeoff.
- The live single-Order-restart scenario with Inventory absent failed to rediscover Inventory automatically when it returned; an additional Order restart was required. [Merged PR #14](https://github.com/abdullahsayed30/Polaris/pull/14) retains separate Docker-backed managed-DNS proof at historical source `0406343d19318d71c45ae6931425f671707076b7`, based on `32c0ab9`: the positive regression passed twice and the static-target negative control reproduced unresolved calls/PENDING intent after hostname availability. Owner-reported full verification passed 122 tests (89 fast + 33 integration/system), zero failures/errors/skips. Test JWT/direct SQL setup and disabled tracing/listeners limit that proof; live Compose/Helm, notification consumption and combined full-flow trace recovery remain unverified by this fixture. PR #14 is now merged at main `d300cfa96167740ad2a5999832d2c9fb1dff4b82`; the old test-source facts above remain distinct from later integration/live verification.
- Old carrier timestamps were injected, not observed over hours/years. The final trace covers about 65.7 seconds including retries; its gateway HTTP span is about 575 ms. Persistence spans are adapter-operation blocks, not per-SQL instrumentation.
- Observability proof used isolated PostgreSQL 18 mount/Keycloak subject/readiness/cached Kafka overrides. It does not prove tracked-default clean-clone behavior. Initial dashboard screenshots have earlier application provenance than final trace/JAR captures; no Loki/log datasource is included.
- Helm owns application resources and references external infrastructure/secrets. No production database/Kafka operation, cluster deployment or disaster-recovery rehearsal is proven by this draft.
- Controlled Kafka replay does not imply an automatic production DLQ redrive consumer. Current inbox protection cannot guarantee exactly-once external effects.
- A walkthrough document is not a recording. Retained branch screenshots/traces do not establish a combined release candidate or measured SLO. Pending acceptance and open security disposition remain explicit in the index.
